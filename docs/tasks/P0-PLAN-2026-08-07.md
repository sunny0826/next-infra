### 1.2 执行步骤（Runbook）

前置条件：

1. 使用 Node 24 环境（项目声明 `>=24.12.0 <25`；当前 v26 会打印 engine warning，见交接文档第 6 节）。
2. 准备一个 **fine-grained Token**，仅授予测试仓库的只读权限（Contents/Metadata/Workflows read 即可），Token 只粘贴进 App 输入框，不写入任何文件。

1. 启动新版本 Desktop：`cd apps/desktop && rtk pnpm tauri dev`。
2. 进入“连接器”页，在连接状态表中找到**旧 GitHub 连接**（无范围选择的连接）。
   - **禁止**对其点击“手动同步”。
3. 点击该连接的“删除本地数据”，核对预览数量（资源 / 关系 / 资源版本 / 关系版本 / 变更 / 绑定 / 同步记录）。若绑定数 > 0，确认接受绑定一并删除。

5. 在“添加 GitHub 连接”中：输入名称 + fine-grained Token → “验证并加载仓库” → **只勾选一个或少量测试仓库** → “创建连接并同步 N 个仓库”。
6. 等待后台同步完成（连接状态表显示最近成功时间与健康度）。

## 2. P0-2：Scheduler 接入 Desktop Host 的实际周期执行

### 2.1 现状事实（已核对代码）

| 组件 | 状态 |
| --- | --- |
| `Scheduler`（register/remove/plan_due/plan_wake_catch_up） | `crates/next-infra-runtime/src/lib.rs`，已有单元测试（`scheduler_orders_connections_and_bounds_wake_catch_up` 等） |
| `Runtime::plan_due(now)` / `sleep()` / `wake(now)` / `stop()` | 已实现；`plan_due` 有 admission 门禁（非 Running 返回 InvalidState） |
| `SyncTrigger::Schedule` | `next-infra-core::status` 已存在 |
| 有界同步入口 | `AppState::enqueue_github_sync(connection, trigger)` → `sync_github`；单飞守卫 `github_sync_running: Arc<AtomicBool>`；并发时返回 `sync_in_progress`（retryable） |
| 周期驱动 | **不存在**（全 App 无定时器） |
| 调度注册 | **不存在**：`AppState::open` 用 `Scheduler::default()`，从不 `register` |
| 睡眠/唤醒 | `handle_sleep`/`handle_wake` 已接 NSWorkspace；但 `handle_wake` 丢弃 `runtime.wake(at)` 返回的 catch-up 计划 |
| 推荐间隔 | `query_sync_interval_millis` 已按 descriptor 计算（github=900s，其余 15min 兜底） |
| 现有测试断言 | `composition_rehydrates_query_context_for_persisted_connections` 断言 `next_scheduled_at == None` —— **保留该行为，不因本任务改变**（见 2.7） |

### 2.2 核心设计决策

1. **只注册有 live 同步路径的连接**：当前 composition 只有 `sync_github` 一个 live 实现。SSH/Dokploy/Cloudflare/Supabase/云厂商尚无 live 路径（离线 descriptor/replay 阶段），注册了也没有可执行入口。新增一个集中判断 `fn has_live_sync_path(connector_type: &ConnectorType) -> bool`（当前实现：`connector_type == "github"`），建连/启动/调度分发三处共用，未来其他 Connector live 化时只改这一处。
2. **调度驱动放在 Desktop crate 新模块** `apps/desktop/src-tauri/src/scheduled_sync.rs`，不在 composition/mod.rs 继续膨胀（该文件已 1666 行）。模块分两层：
   - **纯逻辑层 `ScheduledSyncDriver`**（可注入时钟、`resolve` 闭包、`enqueue` 闭包、pending 队列）→ 全部单元测试用 fake 完成，不碰网络。
   - **Tauri 包装层**：一个 std 线程每 10s tick，组合真实 AppState（runtime mutex、store、enqueue_github_sync）。**不新增 tokio 依赖**：composition 现有代码风格全部是 std 同步原语（Mutex/AtomicBool），且 `enqueue_github_sync` 内部用 `tauri::async_runtime::spawn` 可从任意线程调用。
3. **首次 next_due_at = now + interval**：建连后的首次同步已由现有建连流程负责；调度在启动后一个间隔才首次到期，避免与建连/手动同步叠加。
4. **调度到期被单飞守卫拒绝（`sync_in_progress`）时静默跳过**：`plan_due` 已把 next_due 推进到下一间隔，天然形成“下一间隔重试”，不需要显式重试队列。这即交接文档要求的“排队”语义：不丢连接、不无限补跑、单飞并发由现有守卫保证。
5. **Quit/Power-off 顺序**：先停驱动线程（不再发起新同步），再 `runtime.stop()`（drain/checkpoint 处理进行中的写入，残留运行按现有 interrupted/recovery 语义在下次启动恢复——这是既有行为，不在本任务改变）。
6. **驱动线程对 `plan_due` 的 InvalidState（Sleeping）容错**：睡眠期间 tick 到达时跳过，唤醒后由 wake 路径恢复。

### 2.3 模块设计（scheduled_sync.rs）

```text
pub const TICK_MILLIS: u64 = 10_000;

pub enum EnqueueError { SyncInProgress, Unavailable }

// 纯逻辑层：可注入时钟与闭包，全部可单测
pub struct ScheduledSyncDriver<Resolve, Enqueue> {
    resolve: Resolve,   // Fn(&ConnectionId) -> Option<Connection>
    enqueue: Enqueue,   // FnMut(Connection, SyncTrigger) -> Result<(), EnqueueError>
}

impl ScheduledSyncDriver<..> {
    // 一次 tick：先消费 pending（wake catch-up），再 plan_due
    pub fn tick(&mut self, runtime: &mut DesktopRuntime, pending: &mut VecDeque<ScheduledSync>, at: Timestamp);
    // 注册/注销辅助
    pub fn register_connection(&mut self, runtime: &mut DesktopRuntime, connection: &Connection, at: Timestamp);
    pub fn remove_connection(&mut self, runtime: &mut DesktopRuntime, connection_id: &ConnectionId);
}
```

Tauri 包装层（composition 内）：

```text
AppState 新增字段：
  scheduler_driver: Mutex<Option<SchedulerDriverHandle>>
    // handle = { stop: Sender<()>, join: Option<JoinHandle> }，std::thread

AppState::open：
  1. runtime 启动后：遍历 store 中 enabled 且 has_live_sync_path 的连接，
     scheduler_mut().register(id, interval(descriptor), now + interval)
  2. spawn 驱动线程（recv_timeout(TICK) 循环 → driver.tick(...)）
  3. 失败路径：驱动线程/注册失败不得阻止 App 启动（降级为现状：手动同步可用），记日志后继续

github_connect 成功后：scheduler_mut().register(id, 900_000, now + 900_000)
purge_github_connection 成功后：scheduler_mut().remove(&id)

handle_wake：runtime.wake(at) 返回的计划 push 进 AppState.pending_syncs: Mutex<VecDeque<ScheduledSync>>
              （现状是 let _ = 丢弃——改为入队）
handle_sleep：不变（runtime.sleep()）
persist_user_quit_and_stop / handle_power_off：先 driver.stop()（send + join），再 runtime.stop()

驱动线程 tick 逻辑（组合真实闭包）：
  1. 取 pending_syncs 全部 → 对每个 plan：resolve 连接 → 缺失/disabled/非 live 则跳过；
     enqueue(connection, SyncTrigger::Schedule)；SyncInProgress → 跳过（下一间隔自然重试）
  2. runtime.plan_due(now)（InvalidState → 跳过）→ 同样分发
  3. 分发前重新从 store 读取连接（拿最新 enabled 状态）；顺序：resolve → begin_github_sync → enqueue，
     与 manual_github_sync 相同的竞态安全顺序（purge 全程持有单飞守卫，见 2.5）
```

### 2.4 测试矩阵（交接文档第 4 项要求的五类）

| 场景 | 层 | 测试内容 |
| --- | --- | --- |
| 排队 | driver 单测 | 到期计划在单飞拒绝（SyncInProgress）后不丢失：断言 enqueue 收到拒绝、连接仍在下个 interval 再次到期 |
| 并发 | driver 单测 | 同一 tick 两个连接到期 → enqueue 依次调用；第二个被守卫拒绝时不影响第一个 |
| 显式 Quit | composition 集成 | `persist_user_quit_and_stop` 后驱动线程退出、无新 enqueue；runtime 状态 Stopped |
| 运行中删除连接 | composition 集成 | purge 后 scheduler 条目被移除（`scheduler.entry(id).is_none()`）；驱动对已删除连接的 resolve 返回 None → 跳过 |
| App 重启 | composition 集成 | 预置 github 连接（含 fixture）→ `AppState::open` 后断言 scheduler 有条目、interval=900_000、next_due≈now+900s；再 open 一次幂等 |
| 补充 | driver 单测 | 睡眠期间 tick（plan_due InvalidState）静默跳过；wake 后 pending 计划每个连接至多分发一次（catch-up 有界） |
| 补充 | composition 集成 | 建连成功后注册条目；`composition_rehydrates_query_context_for_persisted_connections` 断言保持 `next_scheduled_at == None` 不变 |

### 2.5 竞态安全论证（写入实现注释与测试）

- **purge 与调度并发**：`purge_github_connection` 全程持有 `github_sync_running` 守卫；驱动分发顺序为 resolve → begin（swap true）→ enqueue。两个交错都安全：
  - 驱动先 begin → purge 被 `sync_in_progress` 拒绝；
  - purge 先完成 → 驱动 resolve 返回 None → 跳过。
- **调度与手动同步并发**：同一守卫，手动同步优先，调度静默跳过到下一间隔。
- **Quit 与进行中同步**：驱动先停（无新任务），`runtime.stop()` 的 drain/checkpoint 处理已有写入；被中断的运行由 `recover_startup → interrupted_runs` 语义覆盖（既有行为）。
