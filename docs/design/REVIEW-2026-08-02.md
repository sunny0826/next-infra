# Next Infra 文档 Review 报告

**Review 日期：** 2026-08-02  
**Review 范围：** `docs/design/` 全部设计文档  
**实现状态：** 未开始开发；本次只审查和修正文档

## 1. 结论

当前设计已经从“本地 Rust daemon + 浏览器 UI”一致收敛为：

```text
Next Infra.app / Tauri v2 Desktop Host
  ├─ React / TypeScript UI
  ├─ thin Desktop Adapter
  └─ independent Rust Control Plane Runtime
       ├─ Query Service
       ├─ Connector / Sync / Store
       └─ private Unix Domain Socket

Codex / Hermes
  └─ next-infra-mcp / STDIO
       └─ Unix Domain Socket -> Query Service
```

Review 后没有未处理的 P0 架构矛盾。单实例、窗口关闭、显式退出、睡眠恢复、MCP 拉起、SQLite 所有权、Tauri IPC、Secret 与 SSH 边界均有明确语义；高可视化要求也已从页面名称扩展为可验收的视觉与交互契约。

项目仍停在 Goal 0。Goal 1 有明确的前置决策，且用户尚未授权编码，因此本结论不表示可以自动开始开发。

## 2. Review 方法

本轮按以下视角交叉审查：

1. 用户约束是否贯穿主 RFC、领域模型、安全和实施目标。
2. Tauri 是产品宿主还是领域框架，Core 是否能独立测试。
3. UI 关闭、App 退出、崩溃、睡眠和 MCP 直连时是否有完整生命周期。
4. React 与 MCP 是否共享查询语义，Event 是否可能成为错误的权威状态。
5. SQLite、Relation、Version、Change 与来源追溯是否自洽。
6. WebView、Socket、Keychain、SSH 和 Provider 数据是否遵循最小权限。
7. “高可视化”是否有信息层级、视觉语义、边界和异常状态，而不只是页面清单。
8. 后续 Goal 是否有依赖、验收路径和停止条件。

严重度定义：

- **P0**：与已确认产品约束冲突，未修复不能冻结设计。
- **P1**：会造成架构分叉、安全边界缺失或主要验收路径失败。
- **P2**：不会改变总体架构，但会造成实现歧义、体验退化或验证不足。

## 3. Findings 与处理结果

| ID | 严重度 | Finding | 处理结果 | 状态 |
| --- | --- | --- | --- | --- |
| R-01 | P0 | 旧方案把后台 Rust daemon 和浏览器 SPA 作为默认形态，与用户选择 Tauri 冲突 | RFC、环境、接口与 Goals 全部改为单实例 Tauri Desktop Host；browser/loopback 仅保留为非目标或替代方案 | Resolved |
| R-02 | P1 | 若把领域逻辑直接放入 Tauri Command，Core 会与 WebView 生命周期耦合 | 明确独立 Control Plane Runtime、Shared Query Service 与薄 Desktop Adapter；Core/Store/Sync/Query 禁止依赖 Tauri | Resolved |
| R-03 | P1 | 主窗口关闭后的调度和 MCP 可用性未定义 | 关闭只隐藏窗口且不销毁 WebView；Runtime、SQLite、Scheduler 与 Socket 继续运行；重开后重新查询快照 | Resolved |
| R-04 | P1 | Host 未运行时 Codex/Hermes 不能“直接调用” | MCP Bridge 可在用户预授权后从冻结可信路径后台拉起唯一 Host；失败或未授权返回 `host_unavailable` | Resolved |
| R-05 | P1 | 仅抑制当前 Bridge 会话会让用户显式退出后被下一个 Agent 调用立即复活 | 增加跨 Bridge 进程的 `user_quit` 标记；只有用户主动启动或已启用的下一次登录自动启动可清除 | Resolved |
| R-06 | P1 | Tauri Event 容易被当成权威数据或安全输入 | Event 仅发送版本/scope 失效通知；UI 必须重新 Query；来自 WebView 的 Event 不参与审批、同步结果或权限判断 | Resolved |
| R-07 | P1 | “高可视化”只有页面列表，无法约束通用 KPI 卡片和全局图 hairball | 新增界面与可视化设计，定义 Evidence Spine、状态编码、有界 Topology、页面契约和 Fixture 纵切 | Resolved |
| R-08 | P1 | RelationVersion 被表和 Change 引用却没有定义；configured/inferred 关系也无法诚实追溯到 SyncRun | 定义 Relation 稳定键、RelationVersion 和按 `sync_run | binding | inference` 区分的 provenance | Resolved |
| R-09 | P2 | MCP 提供 `labels` 过滤，但 Resource 模型没有 labels | 增加带 namespace、经过清洗的 Resource labels，并纳入版本快照 | Resolved |
| R-10 | P1 | 单实例只依赖 UI 插件会留下第二个 SQLite owner 与 Socket 接管风险 | 增加实例锁、SQLite 锁、Socket owner/peer UID 校验；第二实例载荷仅允许固定激活意图 | Resolved |
| R-11 | P1 | WebView 若获得通用 Shell、文件、HTTP 或 Keychain read，会绕过 Rust 边界 | 明确本地 bundle、严格 CSP、受限 Commands/capabilities，禁止通用 Shell/FS/SQL/Keychain read/HTTP proxy | Resolved |
| R-12 | P2 | Keychain 在签名变化、自动登录或锁屏时的失败语义不明确 | 定义稳定 item 命名、签名访问验证、`credential_unavailable` 和禁止循环授权弹窗 | Resolved |
| R-13 | P2 | 浏览器组件测试无法证明托盘、关闭/恢复和单实例行为 | Goals 要求 Mock Desktop Adapter 测试之外，再启动真实 Tauri App 做 macOS smoke | Resolved |
| R-14 | P2 | RFC 只有最小总览，进程 owner、Runtime 内部边界、查询汇合和 `user_quit` 生命周期不易交叉核对 | 新增结构图集，并明确它只是 RFC 的可视化投影 | Resolved |
| R-15 | P2 | Provider/Connector/Connection、Health/Freshness/Coverage 等词跨文档容易混用 | 新增规范术语表、消歧词表和命名治理规则 | Resolved |
| R-16 | P2 | 崩溃恢复要求把遗留 run 标为 `interrupted`，但 Resource Model 的 SyncRun status 未包含该值 | 补齐 `interrupted` 枚举与术语定义 | Resolved |

## 5. 仍需冻结的决策

以下不是当前架构矛盾，但在进入对应 Goal 前必须做出明确选择。

### 5.1 Goal 1 前置决策

1. **Bridge 安装位置**：App Bundle 内、用户级 bin，或独立安装物。推荐优先评估 App Bundle 内稳定路径，以减少 Host/Bridge 文件版本分叉，但必须用 Codex/Hermes 的真实配置方式验证。
2. **更新与协议兼容**：运行中的旧 Host 遇到新 Bridge 时如何提示重启，以及 App 更新如何保证两个发布物不永久错配。
3. **启动默认值**：自动登录默认是否开启；MCP 自动拉起必须保持独立授权。
4. **签名、公证与 Keychain**：本地开发签名、Developer ID 和发布阶段的边界，以及签名变化后 Keychain item 是否继续可用。
5. **版本固定**：Goal 1 开始时固定 Tauri v2、官方插件、Rust 与 pnpm 的具体版本，不在本轮提前猜测未来版本。

### 5.2 Goal 3 前置决策

1. 是否确认“冷静、紧凑、证据优先的基础设施图谱”视觉方向。
2. 默认深色石墨画布还是同时提供浅色模式。
3. Overview 的 Critical Paths 是否进入首版。
4. Inspector 默认常驻还是按选择出现。

### 5.3 Provider 阶段决策

1. 首批真实 Connector 顺序。
2. 是否把本机作为 `local.host`。
3. 各 Provider 的真实只读凭据和最小权限矩阵。
4. Hermes 的安装时间和真实 MCP 兼容性验收。

## 6. 保留风险

| 风险 | 影响 | 当前缓解 |
| --- | --- | --- |
| Desktop Host 崩溃会同时影响 UI 与 MCP | 单进程故障域 | WAL、interrupted SyncRun、自动拉起可选；暂不引入第二个常驻 daemon |
| Bridge 是第二个可执行发布物 | 路径与版本可能漂移 | 协议握手、拒绝猜测字段、Goal 1 冻结原子更新策略 |
| macOS 签名与 Keychain 行为 | 后台同步可能请求授权或失去凭据 | 稳定 item 命名、`credential_unavailable`、真实签名矩阵验收 |
| 睡眠造成轮询空窗 | 状态可能过期 | Freshness 独立显示、唤醒后每 Connection 最多一次错峰 catch-up |
| Topology 复杂度增长 | 图不可读或 WebView 卡顿 | focus-centered、depth 1 默认、节点/边硬上限、frontier 展开 |
| Provider 权限或 API 不完整 | 缺失资源可能被误判为删除 | Coverage 模型、连续权威全量两次才 tombstone |
| 当前磁盘只剩约 23 GiB | 历史和日志膨胀 | 变化时才存版本、默认保留期、1 GiB 软预算和阈值维护 |
| Hermes 尚未安装 | 只能证明协议设计，不能证明兼容性 | 文档禁止提前声明“已验证”，后续独立真实验收 |

## 7. 文档一致性结论

- RFC 是运行与进程模型的唯一主来源。
- Resource、Relation、Coverage 和历史语义集中在资源模型。
- Connector 不写数据库、不提供任意命令、不调用首版外部写 API。
- Desktop 与 MCP 共享 Query Service，但拥有不同的传输 adapter。
- Tauri Event、Unix Socket 和 MCP 都不能绕过字段过滤、大小上限和 Secret 边界。
- UI 视觉语义与领域模型一一对应，没有用单色状态掩盖 Health/Freshness/Coverage 差异。
- 实施 Goals 维持串行依赖，Goal 0 完成后必须等待用户明确授权。

## 8. Review 退出条件

本轮 Review 在满足以下条件后结束：

- 无未处理 P0 finding。
- P1 finding 已修复或明确成为进入 Goal 1 前的用户决策。
- README 索引能到达全部设计文件。
- Markdown 结构与交叉引用可验证。
- 工作区没有 Cargo、Node、Rust、TypeScript、SQL 或构建配置。
- 不执行任何开发、安装、服务启动或 Provider 访问。

结论：设计文档可以提交给用户评审，但项目必须继续停在 Goal 0。
